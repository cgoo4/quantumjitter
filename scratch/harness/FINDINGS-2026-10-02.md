# Thicken intermittent load — evidence gathered 2026-10-02 (read-only phase)

## Three kept-separate observations

1. Run All clears diagnostics and launches local Shiny; broken logo (separate issue).
2. Quarto localhost:5351 preview works in external Firefox, blank inside Positron
   (known: quarto preview sends no COOP/COEP).
3. Production intermittently shows the site's 404 page inside the app frame
   with normal caching enabled — Firefox, DevTools Disable Cache unchecked.

## Failed Firefox session evidence (surviving)

- `/tmp/live_thicken.html` (17:24 BST snapshot of the failing page): contains
  NO `app_<hash>` iframe at all — only the giscus script strings. Shinylive
  scripts (`shinylive.js`, `load-shinylive-sw.js` refs) are present (9 refs).
- `/tmp/head_thicken.html` (13:20) has the same profile.
- No HAR, console log, or SW state was saved from that session.

## Direct production probe (curl, 19:05 BST)

- `GET https://www.quantumjitter.com/app_1a2b3c4d5e/` → HTTP 404, body is the
  site 404 page ("The Strange Case of the Absent Page"). Saved:
  `/tmp/probe404body.html`.
- So the user-visible symptom (site 404 inside the app frame) is exactly what
  an un-intercepted `app_<id>/` iframe navigation returns. The app frame's
  virtual path is served by the shinylive service worker; when the SW is not
  controlling the page, the request goes to the network → Netlify 404.

## Runtime sequencing found in deployed shinylive-0.10.12

- `load-shinylive-sw.js`: registers SW (`shinylive-sw.js` at site root),
  `navigator.serviceWorker.ready.then(() => { if (!controller) reload() })` —
  one reload only, no retry on failure.
- `shinylive.js` `setupAppProxyPath()`: throws "ServiceWorker controller was
  not found!" if no controller at app-start time; the Viewer useEffect runs
  after `proxyHandle.shinyReady` and on throw the iframe never gets a src —
  consistent with the "no app iframe" DOM snapshot.
- `configureProxyPath` messages the SW with the random `app_*` path. A 404 in
  the frame means either (a) the SW fetch handler didn't have that path
  registered when the iframe navigated (channel message lost/delayed), or
  (b) no SW controller at navigation time. Not yet distinguished.

- d8bedb1c: prose only + generated output + NEW wasm package tarballs

## Corrections (2026-10-02, evening)

- A direct curl request does not test service-worker interception; it only
  shows what the server returns for an `app_<id>/` path. The 404 body is not
  evidence about SW state during the real failure.
- Provenance of `/tmp/live_thicken.html` is unestablished (what tool, which
  load, which frame). Its missing iframe must not be treated as
  browser-runtime evidence until its capture method is confirmed.
- The SW sequencing race, a lost `configureProxyPath` message, and any effect
  of the additional package downloads on failure frequency are hypotheses
  only.
- Normal-cache Firefox failures occurred **before** the library
  consolidation (44127c8d), so the added tarballs are not implicated in the
  original failure occurrences.
